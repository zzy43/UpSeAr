法定自查 · 年度审核计划与问题库
====================================================================

一、这是什么
--------------------------------------------------------------------
和安全审核（SafetyAudit/work.html）**是两套不同的系统**，从轮播首页点
「法定自查（Statutory Inspection）」那一页进来（点页面上的信息面板）。

它解决的是这个问题：

    · 年度审核计划是排好的 —— 比如 2027 年 4 月查飞行部、7 月查运技部、
      8 月查达卡航站、9 月查昆明航站；
    · 但**还没到检查那个月之前**，平时就会发现一些问题（比如 2026 年 11 月
      觉得飞行部排班不太对）；
    · 于是先随手记进这个单位的问题库，一条条攒着（几十条很正常）；
    · 到了计划那个月真去检查时，打开这个单位的问题库，一条条核对，
      核对过的勾上「已完成」。

所以界面上就两件事：**左边选单位**，**右边看它的年度计划 / 问题库**。


二、文件结构
--------------------------------------------------------------------
    CheckQuestion/
      check.html            页面（唯一入口）
      js/
        check-config.js     配置：OSS 地址、审核员名单、问题级别、来源、
                            默认受检单位（**只想改内容就改这个文件**）
        check-core.js       基础层：状态、小工具、OSS 读写（含自动保存）、
                            弹层、轻提示、亮/暗主题、背景海报
        check-plan.js       审核计划：左边单位栏、计划总览表、单位增删改
        check-issues.js     问题库：问题清单、记录/编辑/删除/标记
        check-main.js       启动与事件绑定
      css/
        check-base.css      设计变量、基础、海报背景、顶栏、按钮、小牌子
        check-parts.css     弹层、表单、轻提示
        check-app.css       两栏布局、单位列表、问题卡片、计划表
        check-light.css     亮色模式（整段覆盖暗色的部分）

加载顺序不能乱：config → core → plan → issues → main。
样式加载顺序也不能乱：base → parts → app → light。


三、数据存在哪
--------------------------------------------------------------------
阿里云 OSS：
    https://safety-audit-system.oss-cn-hangzhou.aliyuncs.com/CheckQuestion/check.json
    问题附件的取证文件存在同一个目录下的 **文件/** 子目录里，例如：
    https://safety-audit-system.oss-cn-hangzhou.aliyuncs.com/CheckQuestion/文件/20260921-183012-现场照片.jpg
（和安全审核的 SafetyAudit/plan.json **分开存**，互不影响。
  地址在 js/check-config.js 的 OSS_BASE_URL / OSS_JSON_FILE 里改。）

★ **还有一份和安全审核共用的文件（2026-09-21 加的）**：
    https://safety-audit-system.oss-cn-hangzhou.aliyuncs.com/审核员.json
  就这四个人（名单 + 底色 + 字色 + 单字）存在这里，**两套系统都读它、也都写它**，
  所以一边改了名字/颜色/单字，另一边刷新后就是同一套；一边加了人/删了人，
  另一边也跟着变。放在 bucket **根目录** —— SafetyAudit/ 和 CheckQuestion/ 是
  两个独立目录，根目录才是它们共同的地方。
  · 文件名/地址在 js/check-config.js 的 OSS_ROSTER_FILE / OSS_ROSTER_URL 里改
    （**两边的配置都要改**，否则对不上）；
  · 文件结构：`{ "updated": "…", "auditors": [ { "name", "color", "ink", "short" } ] }`；
  · **没这个文件也能正常用**（第一次改样式 / 加人才会把它建出来），
    这时各自用自己 check.json / plan.json 里的名单当默认；
  · ⚡ 启动时它和 check.json **同时发请求**，并且**不挡首屏** ——
    主数据一到就先画，名单回来了再套上去重画一次（因为它只是名单+颜色，
    不值得让整页等它）。实现上拆成了 `fetchRoster()`（只取）+ `applyRoster()`（套上去）
    两步 —— 不拆的话，名单先回来会被 `state.data = 主数据` 盖掉。

★ **首屏缓存：打开先秒画上次的数据（2026-09-21 加）**
  从 OSS 拿数据是一个完整的网络来回，这期间页面只能空着或者拿「示例数据」顶着。
  所以把**上次成功读到的数据**存一份在浏览器里（localStorage 的
  `checkquestion:cache`）：打开先拿它秒画一屏，真正的数据一到就盖掉
  （stale-while-revalidate）。
    · 存的时候机：**确实从 OSS 读到之后**、以及**每次保存成功之后**
      （`loadAll()` / `uploadNow()` 里的 `saveCache()`）；
    · ⚠ 画缓存的那一下 `state.cacheOnly = true`，**一律不许保存**
      （`canWrite()` 里加了这个判断）—— 不然一个快速操作就可能把旧数据整份写回 OSS；
    · ❗ **读不到 OSS 时，有缓存就用缓存顶着**（不再退示例数据），
      但这时是**只读**的，右上角角标会写「读取失败」（免得把旧的当成真的、
      再把旧的写回去）；想让它在读不到时退示例数据，就得把这一支改回原来的写法；
    · 代价：头几百毫秒看到的是上次的数据（比如刚删掉的那条又冒一下），
      时间短到一般注意不到；
    · 缓存超过 600KB 就不存了（localStorage 一般只有 5MB），
      想清掉：控制台 `localStorage.removeItem('checkquestion:cache')`
      （代码里也留了 `clearCache()`）；
    · **读不到就重试一次**（2026-09-21 补上，和 work 一样的做法）：失败等 600ms 再试一遍，
      4xx（比如 404 还没建过这个文件）不重试。以前网上抖一下就直接退示例数据 + 只读，
      得手动刷新才行。
  · ⚠ 但**一旦这个文件存在了，就以它为准** —— 也就是说，
    往 check.json 里手写 auditors 是没用的（两边都听 审核员.json）。

    · **第一次打开时 OSS 上还没有这个文件**，这是正常的 —— 右上角会显示
      「OSS · 待首次保存」，这时页面用的是配置里的默认计划（四个单位）。
    · 你随便改一下（加个单位、记条问题），停手约 0.8 秒后会自动 PUT 上去，
      文件就建出来了，角标变成「OSS 数据」。
    · 之后所有改动都是自动保存的，不用手动导出/上传。
    · 想备份：「⋯ → ⤓ 导出 JSON」下载一份；想恢复：「⋯ → ⇪ 导入 JSON」粘回去。
    · ⚠ 数据文件必须是**公开可读可写**的（和 SafetyAudit 用的是同一个 bucket，
      配置一样就行）。

数据结构（也就是 check.json 的内容）：

    {
      "theme": "Statutory Inspection",
      "title": "法定自查 年度审核计划",
      "updated": "2026-09-21 13:30",
      "auditors": [{ "name": "景志详", "color": "#E8688A", "ink": "#cfe4ff", "short": "景" }],
          // ⚠ 名单的真实住处是共用的 审核员.json（见上面「三」）；
          //   这里只是那份文件还没建出来时的初始值 / 备份。

      "units": [
        { "id": "u-flight", "name": "飞行部", "plan": "2027-04",
          "auditors": ["景志详", "方乔"], "note": "年度审核", "audited": false,
          "conclusion": "这次审核的总体情况（可空）",
          "files": [ { "name": "审核计划.pdf", "url": "https://…", "size": 1234 } ] }
      ],

      "issues": [
        { "id": "q-xxx", "unit": "u-flight", "date": "2026-11-05",
          "level": "重要", "source": "日常观察", "by": "朱震宇",
          "text": "排班出现连续夜航后紧接早班",
          "detail": "取证情况、依据……（可空）",
          "conclusion": "已现场核对 11 月班表，属实……（审核完之后再填，可空）",
          "files": [
            { "name": "现场照片.jpg",
              "url": "https://…/CheckQuestion/文件/20260921-183012-现场照片.jpg",
              "size": 123456 }
          ],
          "status": "open" }
      ]
    }

    · units[].plan 就是「计划检查的年月」，格式 YYYY-MM（只到月，不到日）；      还没想好就留空字符串，界面会显示「未排检查计划」并排到最后。
    · units[].auditors 是**审核员，可以多个人**（数组）；只写一个也行。
      老数据写成单个字符串的 "lead" 也认，读进来自动变数组，
      但**下次保存就会写成新格式**（老的 lead 字段会被去掉）。
    · units[].audited = **这个单位的计划审核已经做完了**（2026-09-21 加的），
      在「编辑受检单位」里勾。跟问题的 status 是两回事：
      那个是「这条问题算不算用上了」，这个是「这趟审核到底完没完」。
    · units[].conclusion / files = 单位的**情况说明**和**相关附件**，
      跟问题里的 conclusion / files 同名同义（2026-09-21 加的），
      也在「编辑受检单位」里填，附件结构一模一样。
    · issues[].unit 必须等于某个 units[].id；
      对不上的问题读进来会被丢掉（防止出现没有归属的孤儿问题）。
    · level 只能是 js/check-config.js 的 LEVELS 里的值，source 同理。
    · status：open = 待审核（默认） / done = 已完成。
    · conclusion 是**审核情况说明**，去检查之前是空的，检查完再回来填
      （卡片上露三行、详情框整段、一起导出 CSV、一起被搜）。
    · files 是取证附件，**可空、可以多个**；只要 url 有效就认，
      name 和 size 缺了会给个默认值。现在从页面上传最省事
      （想手写 url 也行，但那个地址得公网能访问）。


四、怎么用
--------------------------------------------------------------------
1. **排年度计划**：右上角「⋯ → ＋ 受检单位」，填单位名称 + 计划检查月份 + **审核员**
   （审核员是点小牌子选的，**可以选多个**），也可以顺手勾上「已完成审核」。
   也可以直接点顶部「▤ 审核计划」看总览表，在表里改。

1.1 **同一个部门可以加好几行（2026-09-21 改的）**：
   审核是长期的事 —— 飞行部 2025 年审过一遍，2026 年、2027 年还要再审。
   所以**受检单位允许重名**：每加一行就是**一轮年度审核**，各自带自己的问题库。
     · 以前这里会拦「已经有一个叫『飞行部』的单位了」，现在不拦了；
     · 分清哪一轮靠：**计划检查月份** + **备注** + **已完成** 这三个；
     · 建议备注里写上年度（比如「2027 年度」），重名时好认；
     · 程序内部**从来不用名字找单位**，全都走 id，所以重名不会认错；
     · 看不出是哪一轮的地方都补上了月份：
       「全部单位」混排列表的卡片上会写「· 飞行部（2027 年 4 月）」；
       点进某个单位后，标题右边的小字也带上了备注 / 是否已完成；
       删除确认里也会写明是「哪个月的那一轮」，不会删错。
   ⚠ 一轮一行，意味着**新那一轮的问题库是空的** ——
     上一轮的问题还留在上一行里（那一行已完成、沉在表底），当历史查。
     如果你希望同一个部门所有年度共用一个问题库，那种改法要动的地方多得多，
     到时候跟我说。

1.2 **单位的排队规则（2026-09-21 用户要求，从上到下三档）**：
     ① **还没到的正常计划** —— 里面再按计划月份从近到远；
        **还没排计划月份的**排在①这一档的最后；
     ② **已经过期、却还没完成的** —— 下一批该盯的就是这些；
     ③ **已完成审核的** —— 沉到最下面。
   计划表里②、③两档前面各插一条分割条（2026-09-21 加，用户要求「过期的也和正常计划分开」）：
     `───── 已过期未完成（N 个） ─────`  ← 小字用过期色（亮色下是深红）
     `───── 已完成审核（N 个） ─────`
   只有「上面确实还有东西」才插 —— 整表就只有过期项时，顶上那条没有分隔意义。
   这几行整体还压淡一点（opacity 0.72），鼠标移上去恢复。
   实现就在 check-plan.js：`planGroup(u)` 算出 1/2/3 档，`sortUnits()` 按它排、
   `renderPlanView()` 按它跨档时插分割条（两处共用同一个函数，别各写一份判断）。
   ⚠ 左边那一栏单位列表用的是同一个 `sortUnits()`，所以顺序是跟着变的（但那边没有分割线）。
   ⚠ `nextCheck()`（页头那个「下次检查：…」）会**跳过已完成的单位**，
     不然刚查完的那个又会被当成「下一次」。

1.3 **「已完成审核」这个勾**（2026-09-21 加的）：在「编辑受检单位」弹层里，
   就在「计划检查月份」下面。勾上之后：
     · 总览表「距今」那一列不再是「还有 N 天」，而是绿牌子 **✓ 已完成**；
       并且这一行会**沉到表底**，前面还有一条分割线（见 1.2）；
     · 左边单位栏那行小字变成绿色的「✓ 已完成审核」；
     · 导出计划 CSV 多一列「审核完成」（是 / 否）。
   它和问题的「已完成」**不是一回事**：一个单位整个查完了就勾这个；
   某一条问题在这次审核里用上了，就勾那条问题自己的框。

1.4 **单位也能写「情况说明」、也能传附件**（2026-09-21 加的）：
   「编辑受检单位」弹层最下面两块，和「编辑问题」里的**一模一样**：
     · **情况说明** —— 这次审核的总体情况、结论、后续要求……（可空）
     · **相关附件** —— 审核计划、记录表、证据材料……（可空）
   用法和问题那边的附件完全一致（拖进去 / 选文件 / ✕ 去掉 / 图片鼠停可预览），
   存的字段也是同名的 `units[].conclusion` / `units[].files`。
     · 有附件的单位，**计划表「备注」列**会多一个紫色的「附件 N」小牌子；
     · 导出计划 CSV 也有「情况说明」「附件」两列；
     · 情况说明目前只在「编辑受检单位」里看得到（没有单独的查看框）。
   实现上：附件区抽成了 `check-core.js` 的 **`bindFileBox()`**，
   问题、单位两处共用，别再各写一份。⚠ 它是「先攒着、点保存才挂上去」的，
   所以保存时必须把 `box.get()` 的结果写回数据（单位是 `saveUnitForm()`，
   问题是 `saveIssueForm()`）。
   ⚠ 这个弹层和「编辑问题 / 问题详情」一样是 `.modal-card.is-xl`（1488px），
     字号也走同一套放大规则。

1.5 **批量被删掉时附件不会跟着删**：删单位、删问题都只去掉记录，
   OSS 上 `CheckQuestion/文件/` 里的文件还在（要清得自己去 OSS 控制台）。

2. **记问题**（平时最常用的动作）：
   · 先在左边点中某个单位（比如「飞行部」）；
   · 点**问题库视图右上角**的「＋ 记录问题」（顶栏原来也有一个，2026-09-21 按用户要求
     去掉了 —— 两个功能完全一样，留一个就行），填：受检单位 / 发现日期 / 问题级别 / 来源 /
     记录人 / 问题描述（必填）/ 详细说明（可空）/ **取证附件（可空）** /
     **审核情况说明（可空）**；
   · 保存。这条就进了这个单位的问题库。

2.1 **加取证附件**（2026-09-21 加的，和安全审核那套一样）：
   在「记录问题 / 编辑问题」弹层里，「详细说明」下面就是附件区：
     · 把文件**拖到虚线框里**，或者点「选择文件」选（可以一次选多个）；
     · 传完下面就列出来，右边有 `✕` 可以去掉（**只是从这条问题上去掉，
       OSS 上的文件不会删** —— 删文件要自己去 OSS 控制台）；
     · 附件选的是**立刻上传**（PUT 到 OSS），但**要点「保存」才挂到这条问题上**。
       所以传了一半点「取消」，文件已经在 OSS 上了，只是这条问题里不显示。
       实现上：附件先攒在一个局部数组里，保存时才写进 `issues[].files` ——
       新建问题时还没有问题对象，不这么做就得先存一条空问题。
   · **卡片上会标一个紫色小牌子「附件 N」**（有 N 个附件），卡片底部列出文件名，点开就能看；
     ⚠ 原来用的是 📎 那个 emoji，但 emoji 是自带颜色的字形，
       在暗底上就是一团深灰，根本看不清（2026-09-21 用户反馈「这个标记换一下」），
       所以改成了跟着主题变色的文字 + 紫色小牌子（`.chip.file-n`），
       亮色模式在 check-light.css 里另给一套颜色。
   · **是图片的话，鼠标停在文件名上直接浮出图片**（jpg / png / gif / webp / bmp / svg /
     avif 都认），不用点开新标签页；非图片的不弹。
   · 搜索框**连附件名一起搜**（想起「有张照片叫…」但忘了记在哪条时可搜）。
   · 文件存在 OSS 的 `CheckQuestion/文件/` 下，文件名前面加了时间戳防重名；
     CSV 导出多一列「附件」（多个用、隔开）。

2.2 **审核情况说明**（2026-09-21 加的）：编辑器里在「取证附件」**下面**，
   是给审核员**审核完之后回来写**的：这条问题现场核实的结果、
   对责任单位提了什么要求、限期什么时候改完……
   · 卡片上以绿底一段显示，只露三行（跟详细说明一个做法），点开卡片看全文；
   · 详情框里整段显示（带绿左边框）；
   · CSV 多一列「审核情况说明」，搜索也搜这段（记得住大致内容就能搜出来）；
   · 平时先空着 —— 它就是给「审核完了」这个阶段用的，写不写都不影响其他功能。
   字段名是 `issues[].conclusion`。

3. **看某个单位的问题**：左边点它，右边就是这个单位的问题清单。**排序规则：**
     ① **已完成的沉到最后**（2026-09-21 用户要求 —— 剩下的都是还没核的，好数）；
     ② 待审核的里，**发现日期新的在前**；
     ③ 同一天里**后加的在前**（用户要求「新增加的放在最上面」）。
   实现：check-issues.js 的 `visibleIssues()` —— `.filter().reverse().sort(状态 → 日期)`，
   第③步靠 sort 的稳定性。
   注意：如果录的时候**把发现日期改成很早以前**，那它就排到那一天去 ——
   列表是按「发现日期」排的，不是按「录入时间」排的。
   · 标题右边有「✎ 编辑单位」—— 就在这儿改这个单位的名称 / 计划检查月份 / 审核员，
     不用先跳到「▤ 审核计划」去找（2026-09-21 用户反馈「问题库里受检单位无法编辑」后加的）。
     **选「全部单位」时这个按钮不显示**（那会儿没有单个单位可改）。

六、标题那一行（2026-09-21 定的规矩）
--------------------------------------------------------------------
左上角那个大标题（和浏览器标签页）**固定就是「法定自查 年度审核计划」**，
**不用轮播页传过来的 title**。

原因：点进来时 URL 里会带 `title=法定自查 证据标准和整改验证规则`，
那是轮播页上「标题上 + 标题下」两行字的拼法；
而「证据标准和整改验证规则」是法定自查工作的**内容描述**，不是这一页的标题，
拼上去后标题栏会又长又不像标题（用户 2026-09-21 要求改掉）。

实现：check-core.js 里的 `STD_TITLE` / `pageTitle()` / `titleFromData()`；
    · `titleFromData()` 会做一次兼容：老数据里存的是以前自动拼的那个长标题，
      开头就是那串 URL 标题 → 换成标准标题；
      **手改过 JSON 里的 title**（开头不是那串 URL 标题）就尊重手改的。
    · 所以 OSS 上旧文件的 title 不用手动改，页面上已经是新的了；
      下一次保存会自动写成新标题。


七、几个实现上的注意点（改代码前扫一眼）
--------------------------------------------------------------------
1. **render() 里跟视图无关的东西要放在最前面**。
   check-main.js 的 render() 一开头就刷新「标题 / 主题 / 概况」，然后才分
   问题库 / 计划表两种视图。曾经把顶部那几句写在某个视图分支里，结果另一种
   视图下标题栏永远卡在「加载中…」—— 别再踩。

2. **搜索框不能整块重建**。
   搜的时候走 check-issues.js 的 renderIssuesList()，只换「统计行 + 列表」；
   换成整块 render() 会把输入焦点和光标弄丢。

3. **openModal 一定要把 buttons 传进去**。
   题层底部那排「取消 / 保存」是 openModal 按 opt.buttons 生成的，
   **不传就没有按钮**（只看到一片输入框，没法保存）。
   已经踩过一次：两个编辑弹层都忘了传 buttons。（2026-09-21 已修）

4. **404 不是错误**。
   OSS 上还没有 check.json 时后端返回 404，check-core.js 的 loadAll() 把它
   当成「新文件」处理（state.ossNew = true），这样第一次保存能自动建文件。
   如果把 404 当失败，就会退到示例数据、变成只读，永远存不进去。

5. **自动保存有防抖**：停手 0.8 秒才 PUT，连续编辑会合并成一次。
   传的时候如果又来了一次改动，会等这次传完再补一次（不会并发覆盖）。

6. **删除单位会连它的问题一起删**，所以会弹一个 confirm 让你确认（会告诉
   你有多少条）。

7. **点弹层背景关弹层 = 必须同时看 mousedown 的目标**。
   不能写成 `click + e.target === modal`：在输入框里用鼠标**框选文字**、
   拖出卡片再松手时，浏览器会把 click 派给「按下点和松开点的共同祖先」（就是背景），
   弹层就会自己关掉 —— 看着像「闪退」。
   现在的写法：mousedown 记一个 `downOnBackdrop`，mouseup 时
   **两个条件都成立**才 closeModal（见 check-main.js）。
   （2026-09-21 修；安全审核那套同样毛病，一起改了）

   还有一条跟它同源的坑：**不要先 closeModal() 再 openModal()**。
   `closeModal` 是等 0.16s 淡出动画走完、再延时 170ms 才真正藏起来并清空内容的，
   这 170ms 的计时器如果不取消，**刚打开的新弹层会被它一起藏掉** ——
   表现就是「新弹层一闪就没了」。
   现在 `closeModal` 把计时器存在 `hideTimer`，`openModal` 一进门就 `clearTimeout`；
   另外确实要换内容的（比如详情框点「✎ 编辑这条」）**直接 openModal 就行**，
   不用先关（openModal 本来就会把标题/内容/按钮全换掉）。

8. **审核员牌子上的字色，默认是一道亮蓝色，收在一个变量里**：`--chip-ink`
   （在 css/check-base.css 的 :root 里，现在是 `#cfe4ff`）。
   牌子底色是人手选的（粉 / 蓝 / 紫 / 青），试过三个方案：
     ① 写死白字 —— 中间亮度上发虚；
     ② 按底色亮度自动算黑/白（曾做过 inkOn，代码已删）—— 出来的黑字，用户说更看不清；
     ③ 亮蓝色 —— 现在的做法（用户定的）。
   ★ **要调就改 --chip-ink 这一个数**，两种主题共用（牌子底色本来一样，
     所以 check-light.css 里故意不重定义它）。
   用到的地方：`.chip.who`（计划表、问题卡片）、`.who-opt.is-on`（单位弹层多选）。
   ★ 2026-09-21 之后：某个人可以**单独定字色**（见 6.1），存在 `auditors[].ink` 里。
     渲染时走 `check-core.js` 的 `auditorStyle(name)` —— 底色一定写，
     **字色只在自定义过时才写**（没写就交给 `--chip-ink` 兜底）。
     所以：
       · 牌子渲染**统一用 `auditorStyle(name)`**，别再手写 `background:`（以前是那样）；
       · `.who-opt.is-on` 的字色是 `color: var(--ink, var(--chip-ink))`，
         `--ink` 由 JS 写在 style 上；
       · `auditorColor()` 现在**先查数据里的 auditors、再回退配置文件**，
         这样用户在页面上改的颜色才生效；
       · `normalizeAuditors()` 里，纯字符串形式的老名单会**按名字去 CFG.AUDITORS 把颜色找回来**，
         不找的话全变成灰的了。
   ★ 2026-09-21 又加了一层：**名单和这套样式全部搬到两套系统共用的 审核员.json**
     （见「三」）。启动时 `loadRoster()` 读它 —— **文件存在就盖掉本地的名单**；
     改样式 / 加人 / 删人之后 `pushRoster()` 写回去。所以：
       · 两边都有 `resolveRosterUrl / loadRoster / pushRoster`（名字一样，实现各一份，
         因为两个系统没有共用的 js 目录）；
       · ⚠ 判断存在用的还是 fetchJson + `HTTP 404` 那条路（和主数据文件一样），
         404 就当「还没建过」，不算错误、不提示；
       · ⚠ 写失败只 toast 一句，**不影响本地**，下次改动还会再试。

9. 单位计划月份用的是 <input type="month">（只到月）。Chrome / Edge 支持；
   万一哪个浏览器不支持，会退化成普通文本框，这时要**手输成 2027-04** 这种
   格式（读取时统一会补成两位月份）。

10. **问题卡片上「详细说明」最多几行，改一个数就行**：
    `css/check-app.css` 的 `.issue-detail { -webkit-line-clamp: 6 }`（现在是 6 行）。
    为什么不是 3 行（2026-09-21 用户反馈「宽度占满之后再用 … 缩写」）：
    录入详细说明时段落之间通常是**空行**（敲两下回车），而 `pre-wrap` 下
    **空行也占一行** —— 3 行的额度被空行吃掉一半，实际只显示一个半段落就截了。
    6 行刚好容下三个段落（三段 + 两个空行 = 6 行）。
    同理 `.issue-note`（审核情况说明）是 4 行。
    ⚠ 卡片宽度本来就是占满的，不需要改宽度；截断是按**行数**算的。

11. **附件上传直接 PUT 到 OSS**（匿名直传，不用密钥）：
    `CheckQuestion/js/check-core.js` 的 `uploadFile()` —— PUT 到
    `CheckQuestion/文件/<时间戳>-<原文件名>`（原名里的 `\ / : * ? " < > |` 换成 `_`）。
    和 check.json 用的是同一个 bucket、同一套匿名读写，所以 OSS 那边不用额外配什么。
    ⚠ 传失败（比如 bucket 误设成私有、或者禁了 PUT）只会弹一个失败提示，
      不会把已经填的内容弄丢。
12. **图片预览的元素在 check.html 里**（`#image-tip`，空壳），
    事件绑在 document 上（check-main.js 的 `bindImageTip()`）——
    卡片是每次重画换掉的，把事件绑在卡片上会丢。
